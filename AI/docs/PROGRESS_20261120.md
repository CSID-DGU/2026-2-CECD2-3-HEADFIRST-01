# 중간발표 이후 작업 정리: 설계 · 근거 · 결과 (강채연, 2026-11-20 기준)

보고서 작성 때 참고할 문서. 담당 범위는 오답 분석, 학습 데이터 보강(v3.2), 실험 설계와 결과 해석이다.
학습 · 평가 실행은 조수현, 하드 테스트셋 작성은 손승현 · 김천일이 맡았다.

용어
- **A′**: 중간발표 시점의 메인 모델. 학습 데이터 v3.1(5,052턴)로 학습.
- **INFORM / UNCERTAIN**: 발화에서 값을 뽑을 수 있으면 INFORM, 재질문이 필요하면 UNCERTAIN.
- **문장 틀**: 발화에서 이름 · 숫자 · 날짜를 가리고 남은 형태소 열. 값만 다르고 문장이 같은 발화는 같은 틀이다.

---

## 1. 문제 인식: 왜 다시 설계했는가

중간발표 뒤 교수님 피드백(10/23)과 멘토 미팅(11/12)에서 세 가지 문제가 드러났다.

| 문제 | 근거 수치 | 대응 |
|---|---|---|
| 평가셋이 학습셋과 같은 생성기에서 나왔다 | 생성 평가셋 620문제 중 214문제(34.5%)가 학습 데이터와 문장 틀이 같다. 같은 모델이 생성 620에서는 57.4 → 98.3으로 오르고, 실발화 227에서는 93.8 → 93.8로 그대로였다 | 학습 데이터와 무관하게 사람이 쓴 하드 테스트셋을 메인 지표로 바꿈 |
| 학습 데이터 라벨이 쏠려 있다 | v3.1의 UNCERTAIN 비율 9.9%(실제 노인 발화는 약 63%). 패턴 39개가 전부 한 라벨만 가져, 패턴만 알면 라벨을 100% 맞힌다 | UNCERTAIN을 늘리고, 같은 유형 안에 두 라벨이 모두 있게 함 |
| 모델이 틀리는 유형이 학습 데이터에 없다 | 가족 정보 + 전화번호 · 생년월일 문장 0건, 동의 거절 0건 | 오답 유형을 학습 데이터에 넣음 |

원칙은 두 가지로 정했다.
- 데이터를 새로 대량 생성하지 않고 기존 데이터를 고쳐 쓴다(멘토 지시).
- 교수님 피드백 5("오류 케이스 정리 → 사람이 보완 전략 → 성능 향상")를 실험의 뼈대로 삼는다. v3 → v3.1이 1회차, v3.1 → v3.2가 2회차다.

## 2. 평가 설계

### 2-1. 하드 테스트셋 사용 방식

- 구성: 유형 10개 × 30문제 = 300문제. 유형마다 dev 10 / test 20으로 나눔 → dev 100, test 200.
- test를 유형당 20문제로 둔 이유: "n<20인 칸은 결론 보류"라는 발표 규칙을 넘기는 최소치다.
- 유형마다 INFORM과 UNCERTAIN을 섞고, 한 군데만 다른 짝 문장을 넣었다. 유형만 보고 라벨을 찍을 수 없게 하기 위함이다.
- 작성자와 검수자를 다르게 했다. 300문제 중 290문제 일치, 10문제는 합의.

### 2-2. 누수 방지 규칙

| 규칙 | 이유 |
|---|---|
| 보강 담당(강채연)은 dev 100만 본다. test 200은 조수현에게서 점수표만 받는다 | test를 보고 데이터를 고치면 test 점수가 "처음 보는 문제의 점수"가 아니게 된다 |
| 하드셋 문장을 LLM 생성 지시에 예시로 넣지 않는다 | 평가 문장이 학습 데이터로 흘러 들어가는 것을 막는다 |
| test 점수를 보고 모델 · 에폭 · 데이터를 다시 고르지 않는다 | 점수에 맞춰 고르는 것도 같은 누수다 |
| test 변환 · 채점 스크립트는 문제 내용을 출력하지 않는다 | 실수로 보는 것을 도구에서 막는다 |

- 구현: `convert_hardset.py`(설계표 → 평가 json, 개수만 출력), `score_hard.py`(test 파일이면 내용 출력 옵션을 거부).
- 사고 1건: 11/18에 원본 파일을 확인하다 test 7문제(유형 1)가 화면에 출력됐다. 그 내용은 기록하지 않았고 보강에 쓰지 않았다. 교체 여부는 팀 결정 대기. 교체하지 않으면 한계에 적는다.

### 2-3. 오답 4분류

같은 문제를 학습 전 모델과 A′가 각각 맞혔는지로 나눈다.

| 학습 전 | A′ | 분류 | 조치 |
|---|---|---|---|
| 맞음 | 맞음 | 원래 맞춤 | 학습 데이터에서 줄일 대상 |
| 틀림 | 맞음 | 학습으로 풀림 | 현재 데이터 유지 |
| 틀림 | 틀림 | 학습해도 안 풀림 | 보강 대상 |
| 맞음 | 틀림 | 학습 후 퇴보 | 원인 확인 |

- 이렇게 나눈 이유: "틀린 문제 전부"를 보강하면 이미 학습으로 풀리는 유형까지 늘리게 된다. 보강 대상을 "학습해도 안 풀림"과 "퇴보"로 좁히기 위함이다.
- 오답마다 원인을 "문제 오류 / 애매 / 모델 오류"로 태깅하고 모델 오류만 보강 대상으로 삼았다(멘토 지시).

### 2-4. 지표

- 문제 정답: 예측한 (라벨, 슬롯, 정규화 값) 집합이 정답과 완전히 같음.
- 라벨별 precision · recall · F1과 macro-F1. UNCERTAIN 재현과 INFORM 재현을 항상 같이 본다. 한쪽만 보면 "전부 UNCERTAIN으로 찍는 모델"이 좋게 보이기 때문이다.
- 한 라벨로만 찍었을 때의 점수(하드 dev 100에서 0.530)를 기준선으로 같이 적는다.
- 두 모델 비교는 풀림 / 퇴보 건수와 부호 검정으로 한다.
- 모든 수치에 분모를 적고, 차이는 "몇 문제"로 적는다.

### 2-5. 평가 조건 변경

- 11/18부터 평가가 vLLM + fp8(서빙 조건)로 바뀌었다. 10월 수치는 4bit 평가다.
- 두 조건의 숫자는 한 표에 섞지 않는다. 예: raw test 62의 학습 전 macro-F1은 4bit 0.922, fp8 0.958이다.

## 3. 학습 데이터 진단

### 3-1. 문장 틀 겹침 검사

- 방법: 형태소 분석 후 이름 · 숫자 · 날짜를 `<NAME>`, `<N>`으로 바꾸고, 그 열이 학습 데이터에 그대로 있는지 센다. (`template_tools.py`, `check_template_overlap.py`)

| 평가셋 | v3.1과 틀이 같은 문제 |
|---|---:|
| 생성 620 | 214 / 620 (34.5%) |
| 하드 dev | 6 / 100 |
| 하드 test | 6 / 200 |
| raw test | 5 / 62 |

- 하드셋에서 겹친 것은 "010-1234-5678이요"처럼 값만 말한 문장이다.
- 이 표가 "생성 620 점수를 메인으로 쓰지 않는다"는 결정의 근거다.

### 3-2. v3.1 분포 집계 (`dist_train.py`)

- 동의 슬롯 30턴, 거절 0건. 민원유형 UNCERTAIN 18건, 회신방법 UNCERTAIN 12건.

- 문장 틀 2,512개. 상위 50개 틀이 전체의 26.6%.

## 4. 학습 데이터 보강 설계 (v3.2)

### 4-1. 보강 근거: 하드 dev 오답

학습 전 → A′의 dev 100 결과: 원래 맞춤 61 / 학습으로 풀림 22 / 안 풀림 14 / 퇴보 3. 틀린 17건의 원인은 다음과 같다(전부 모델 오류, 하드셋 정답 수정 없음).

| 원인 | 건수 | 학습 데이터의 상태 |
|---|---:|---|
| 조립 · 숫자열 읽기 | 4 | "N 두 개" 표현 20건이 전부 INFORM |
| 모자란 번호를 채워서 지어냄 | 3 | 번호 일부만 말한 UNCERTAIN 예시 부족 |
| 타인 정보를 본인 값으로 추출 | 3 | 가족 + 전화번호 · 생년월일 문장 0건 |
| 어림 · 일부 날짜를 날짜 하나로 확정 | 3 | 발생일 UNCERTAIN 부족 |
| 민원유형 '기타' 판단 | 2 | |
| 기념일 날짜 | 1 | |
| 이름 + 생일을 같이 말한 발화 | 1 | |

dev는 유형당 10문제라 이 표는 보강 우선순위를 정하는 데만 썼다. 유형 간 우열의 근거로는 쓰지 않는다.

### 4-2. 방법 3가지 (`make_v32.py`)

| 방법 | 내용 | 이렇게 한 이유 |
|---|---|---|
| 줄이기 | 같은 틀은 10개까지만 남긴다. UNCERTAIN은 줄이지 않는다. 5,052 → 4,315턴 | 쉬운 문장 반복이 대세가 되지 않게 한다. UNCERTAIN은 원래 부족해서 남겼다 |
| 유형 변환 | 기존 문장을 하드셋 유형에 맞게 바꿔 쓴다. 변환 57종, 1,857건 | 새로 생성하지 않고 기존 데이터를 고쳐 쓴다는 원칙 |
| 표현 다양화 | 줄이기로 빠진 문장을 값과 순서는 그대로 두고 문장 구조만 바꿔 되돌려 넣는다. 728건 | 건수는 유지하면서 틀 쏠림만 줄인다 |

유형 변환의 설계 원칙
- **정답 라벨은 변환 규칙이 정한다.** LLM은 문장만 쓴다. "노인처럼 말해줘"가 아니라 "연도를 빼고 월 · 일만 말하게 바꿔라, 다른 정보는 넣지 마라"처럼 변형을 지정한다. 중간발표에서 지적된 "LLM에게 패턴대로 만들어 달라고 해서 그 패턴이 나온다는 보장이 없다"에 대한 대응이다.
- **값은 v3.1의 정답 값을 재사용한다.** 값의 말 표현(예: "공일공 팔삼칠일")은 코드가 만든다. LLM이 값을 바꾸거나 지어내는 것을 막는다.
- **같은 유형 · 같은 표현에 두 라벨이 모두 있게 한다.** 예: "N 두 개" 표현은 INFORM 125 / UNCERTAIN 90, 가족 얘기가 든 전화번호 문장은 INFORM 34 / UNCERTAIN 60. 표현만 보고 라벨을 찍는 지름길을 막기 위함이다.
- **건수는 dev 오답에 맞춰 조정한다**(`weights_v32.json`). 오답이 많은 변환은 60 · 45건, dev에서 A′가 전부 맞힌 유형은 15건, 나머지는 30건.
- 변환 종류 표기: `<슬롯>-T<유형>-<라벨>`. 예: `P-T8-U` = 전화번호, 유형 8, UNCERTAIN.

## 5. 실험 설계

| 군 | 학습 데이터 | 확인하는 것 |
|---|---|---|
| 기준 0 | 학습 없음 | 학습 효과의 기준선 |
| 기준 1 (A′) | v3.1 | 보강 전 |
| 실험 A | v3.1 전부 + 유형 변환 | 유형 변환의 효과(더하기만 함) |
| 실험 B | 줄인 v3.1 + 유형 변환 + 표현 다양화 | 문장 틀을 고친 효과까지 |

- 통제: 같은 모델(27B), 같은 학습 조건(4bit QLoRA r16, lr 2e-4, 2번째 에폭), 같은 검증 파일, 같은 평가 조건(vLLM + fp8, temperature 0).
- A를 "더하기만"으로 둔 이유: A′와 다른 점이 유형 변환 하나뿐이어야 그 효과를 말할 수 있다.
- 평가셋 4개의 역할

| 평가셋 | 역할 |
|---|---|
| 하드 test 200 | 메인 지표 |
| raw test 62, 실발화 227 | 실제 발화에서 점수가 내려가지 않았는지 확인 |
| 생성 620 | 참고용("학습 데이터와 같은 생성기"라고 명시) |

| 하드 dev 문제 정답(보강에 쓴 자료) | 100 | 83 | 88 | 92 |
| raw test macro-F1 | 62 | 0.964 | 0.930 | 0.945 |
| 실발화 문제 정답 | 227 | 215 | 215 | 217 |
| 생성 620 정답률 | 620 | 97.8 | 97.9 | 98.1 |

### 6-3. 해석

- **v3.2의 향상은 확인하지 못했다.** 하드 test에서 A는 3문제 올랐지만 풀림 13 / 퇴보 10이고 부호 검정 p≈0.68이다.
- **dev는 5 ~ 9문제 올랐다.** dev 오답을 보고 데이터를 만들었기 때문이다. dev와 test의 차이가 "보강에 쓴 자료의 점수는 근거가 될 수 없다"는 것을 직접 보여 준다.
- **B는 UNCERTAIN을 더 잡는 대신 INFORM을 놓쳤다.** INFORM 재현 0.981 → 0.935(107문제 중 5문제 감소).
- **A에서 새 오류가 나왔다.** dev에서 "월 · 일만 들었는데 연도를 지어낸" 퇴보 2건. raw test 62 점수 하락도 생년월일 UNCERTAIN 2문항을 INFORM으로 낸 것이다.
- **dev 오답 17건의 변화**: A가 8건, B가 10건을 풀었다. 타인 정보 3건은 둘 다 전부 풀었고, 민원유형 '기타' 2건 · 기념일 1건 · 이름 + 생일 1건은 둘 다 못 풀었다.
- **A와 B의 우열은 말할 수 없다.** B는 줄이기와 다양화를 동시에 바꿨고, 차이가 4문제다.

### 6-4. 후속: seed 반복

- 이유: 학습 1회의 3문제 차이가 우연인지 알 수 없다. 같은 어댑터를 다시 평가해도 생성 620에서 1문항씩 흔들렸다.
- 설계: A′ · v3.2 A · v3.2 B를 seed만 바꿔 2회씩 추가 학습(기존 seed 42 포함 조건당 3회). 2번째 에폭 고정.
- **판단 기준을 결과를 보기 전에 정했다.** 하드 test 정답 수의 seed 3개 범위(최소 ~ 최대)가 A′와 겹치지 않으면 v3.2 채택, 겹치면 "차이 없음"으로 A′ 유지.
- 11/20에 요청, 결과 대기 중.

## 7. 하드셋 유형의 근거 확인

- 질문: 하드셋 유형 10개는 팀이 정한 것인데, 실제 발화에서 나오는 유형인가.
- 방법: 실제 발화 raw 368건에 하드셋 유형을 붙였다(`tag_raw_types.py`, AI 초안 → 사람 확인 중). 한 발화에 여러 유형이 붙을 수 있다.

| 유형 | raw 368건 중 |
|---|---:|
| 1 값 일부만 | 201 |
| 5 모호 · 추정 | 34 |
| 8 조립 · 계산 | 30 |
| 3 타인 정보 | 20 |
| 6 되묻기 · 딴소리 | 14 |
| 10 긴 사연 속 값 | 13 |
| 7 거절 · 회피 | 12 |
| 2 묻지 않은 정보 섞임 | 10 |
| 4 번복 · 교정 | 9 |
| 9 숫자 · 한글 혼합 | 0 |

- 유형 10개 중 9개가 관찰됐다. 유형 9는 전사 교정 때 숫자를 한글로 통일해서 raw로는 확인할 수 없다.
- 실제 발화는 유형 1이 55%인데 하드셋은 유형마다 30문제다. 그래서 하드셋 정답률은 "실제 서비스 정답률"이 아니라 "유형별 성공률"로 읽어야 한다.
- raw와 하드셋의 기준 차이 1건: raw는 이름 발화를 확보하려고 타인 이름 4건을 name INFORM으로 넣었다. 하드셋은 타인 정보가 UNCERTAIN이다.

## 9. 한계

1. 하드 test 200문제로는 정답률 0.88 근처에서 95% 오차 범위가 약 ±4.5%p다. 3문제 차이는 가려낼 수 없다.
2. 하드 dev 100은 보강에 쓴 자료라 v3.2의 dev 점수는 근거로 쓰지 않는다.
3. 하드셋은 유형마다 같은 수로 만들어 실제 발화 비율과 다르다.
4. raw test 62는 규칙만으로 95.2%가 나오는 시험지라 모델 우열을 가리는 데 쓰지 못한다.
5. raw의 name INFORM에는 타인 이름이 4건 포함돼 있다(368건 중).
6. test 200 중 7문제가 보강 담당에게 노출됐다(교체 여부 미결정).
7. v3.2의 새 문장 2,585건 중 사람이 전부 읽은 것은 80건이고, 나머지는 LLM 전수 검사와 사람 표본 확인이다.
8. 타인 정보 → UNCERTAIN은 하드셋 기준을 따른 것이고 system 프롬프트에는 이 규칙이 없다.
9. 학습은 전부 4bit QLoRA, 평가는 fp8이다.
